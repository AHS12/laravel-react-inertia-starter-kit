# Taste
- For significant refactors/cleanups, prefers a detailed phased plan written as a markdown file inside the repo (e.g. `docs/*.md`) over interactive plan mode — explicitly asked for "a detailed plan in a markdown" and chose to stay out of plan mode. Confidence: 0.85
- Prefers to take time and audit/inventory everything first (classify generic vs. product-specific code, enumerate every occurrence) before making changes — "we will take our time and mark all unnecessary things". Confidence: 0.7
- Names projects/templates after the repo name with neutral, product-agnostic naming — explicitly moving away from product/brand names ("we no longer gonna use product name. we can use the repo name"). Confidence: 0.7
- Thinks in starter-kit terms: invests in reusable, product-agnostic infrastructure (auth, RBAC, users, settings, export/import, setup wizard) and wants product-specific domain code cleanly separable/removable. Confidence: 0.7
- When pruning a project into a starter template, prefers deleting unneeded docs/files outright over rewriting or archiving them — declined a slim `ARCHITECTURE.md` replacement and chose to delete the product spec entirely ("just remove the tdr, its not needed for a starter"). Keep starter repos lean rather than preserving documentation "just in case". Confidence: 0.65
- Main project is a Laravel + Inertia/React monolith starter kit; quality gate is `composer check` (Pint, PHPStan, Pest, frontend + TypeScript checks). Confidence: 0.8
- Probes plans for coverage gaps before letting execution start ("does this plan also cover X?") and expects gaps resolved by updating the plan file in-place with the verified result — the plan markdown is the single source of truth, kept current as questions get answered. Ad-hoc scope requests made mid-planning are likewise folded into the plan document first ("make it also part of the plan") rather than handled as side notes or ad-hoc implementation. Confidence: 0.7
- Wants declared configuration verified against actual enforcement so nothing extra survives — e.g. every permission-registry entry must be traceable to real enforcement (policy, route `can:` middleware, or frontend consumer); unused ones get removed and a re-grep verification step is written into the plan. Confidence: 0.7
- Prefers a consolidated RBAC surface: related permissions merged into one group rather than kept as separate fine-grained groups — asked to combine two permission groups into the same group while reviewing the permission registry. Confidence: 0.6
- Dev environment is Windows (`K:\Projects\...` paths) — Unix shell commands like `rm -rf` fail; use PowerShell (`Remove-Item -Recurse -Force`, `Select-String`, `Set-Content -Encoding UTF8`) for file operations and .env manipulation. Confidence: 0.9
- During repo-wide rebrands/cleanups, keep the developer's running local environment intact: local `.env` values that point at the existing local database and EnvKit vhost (`APP_URL`) are left untouched — only `.env.example` (the reusable artifact) gets the neutral/clean values. Confidence: 0.6
- Long-running/verification shell commands on this Windows setup: running them in the background (`run_in_background: true`) yields empty logs and fails fast — run them in the foreground via the PowerShell tool instead, and pipe output through `Out-String -Width 400` so long test/lint lines aren't truncated. Confidence: 0.8
- Iterate the quality gate per-piece and fix what breaks: `composer test` (Pint, PHPStan, Pest), `npm run types:check` for TypeScript, and `npm run check:fix` to auto-fix frontend format/lint. When a refactor changes Inertia prop shapes, update the affected feature-test assertions in lockstep and re-run until fully green. Confidence: 0.7
- Verifies completed work against the live rendered app, not the completion summary — repeatedly reports UI issues back with a screenshot of the rendered page (e.g. "this homepage also needs to be fixed" + image, the notification-settings bug report) and delegates diagnosis ("can you check please?"). Treat the screenshot as ground truth for what's actually served, reconcile it against source/build state, and diagnose the root cause before editing code. Confidence: 0.7
- Frontend changes are invisible until assets are rebuilt: after editing `resources/js/**`, run `npm run build`; if a reported UI issue doesn't match the source on disk, suspect a stale `public/build` bundle before editing code, rebuild, and have the user hard-refresh (Ctrl+Shift+R). Confidence: 0.7
